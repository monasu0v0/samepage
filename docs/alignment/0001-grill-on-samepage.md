# grill-on-samepage の設計

grilling の面接ループを samepage 上で回し、合意した文書をプロジェクトの SSOT として運用する機能。

## 0. この文書の位置づけ

これは **合意ドキュメント** です。この文書の上で質問に答え、コメントを付け、合意に達したら `--finalize` で公開用 HTML を切り出します。2026-08-30 に合意が成立し、以降この文書が本機能の SSOT です。

この文書自体が本機能の最初のドッグフーディングでした。5 ラウンド・16 問・コメント 3 件で合意に至り、その過程で拾った不便がそのまま決定 D-5・D-7・D-14 と、SKILL.md への要求（確定した決定を取り消す導線）になっています。

## 1. 目的

[mattpocock/skills](https://github.com/mattpocock/skills) の `grilling`（設計を詰める面接ループ）は、ターミナル上の会話で回ります。そのため **合意の実体が会話の中にしか残りません**。`grill-with-docs` は用語集と ADR をファイルに落としますが、2026-08-30 に確認した時点では、そのドキュメント自身が最大の未解決課題として「それ以外の決定はどこへ行った？ → 会話の中だけ」を挙げていました。

本機能は、この面接ループのインターフェースを samepage の HTML に移します。狙いは 3 つです。

1. **合意が文書として残る。** 質問も回答も、決定も未決も、1 つの HTML の上にある。
2. **合意点を名指しでコメントできる。** 「この決定のこの部分が引っかかる」を、文章ではなく位置で指せる。
3. **ズレたら同じ場所に戻れる。** 実装中に認識のズレが出たら、SSOT に質問ピンを打ち直して再合意する。

## 3. この文書で使う語

- **design tree** — 設計を「決定」のノードとその依存関係の木として捉えたもの。grilling から借用（§5）。
- **frontier** — 前提となる決定がすべて片付いていて、いま推測なしに問える決定の集合。
- **ラウンド** — frontier 全部を一度に問い、全部の回答を待つ 1 サイクル。1 ラウンド = `--questions` 1 回の注入。
- **ALIGNMENT 文書** — 1 回の grilling セッションの決定・用語・未決事項を載せた文書。`docs/alignment/NNNN-slug.md` に置き、ビルダーで HTML を生成してレビューする。合意後は SSOT。
- **SSOT** — Single Source of Truth。実装がそこからズレたら実装のほうが間違い、とみなす基準。
- **ドリフト** — 実装が進むうちに、合意した内容と実際の作業が食い違っていくこと。
- **残件** — 未回答の質問ピンと、`status: "open"` のコメントの合計。
- **取り消して再検討** — 確定した決定の前提が新しい事実で崩れたとき、その決定を frontier に戻すこと。下流の決定も連動して開く。

## 4. 決定

| 決定 | 結論 | 根拠と却下理由 |
|---|---|---|
| D-1<br>合意ドキュメントの種類 | 単一 ALIGNMENT.md<br>（セッションごとに 1 ファイル） | samepage は「1 HTML = 1 レビュー層 = 1 export JSON」の粒度でできており、SSOT をこの粒度に合わせると逆写像が自明になる。未決事項と検討中の選択肢を `data-sp-discussion` で本文に同居させられる点も A だけの性質。<br>**却下:** B（CONTEXT.md + ADR）は ADR の 3 条件ゲートを通らない決定がこぼれ、本機能の動機を潰す。C（併用）は SSOT が 2 箇所に分かれた時点で SSOT ではない。A'（PJ に 1 ファイル）は肥大化する。<br>**波及:** 「PJ の SSOT」の意味が文書の集合になった → D-6。 |
| D-2<br>grilling との関係 | 独立して完結<br>（出典は明記） | 質問の提示形式が本家と根本的に違う（番号付きリスト → 質問ピン + `choices`）ため、どのみち手順を書き直す。加えて、他スキルへの依存は samepage 側から制御できないロード経路を持ち込むので、「クローンすれば動く」という保証を優先した（2026-08-30 に確認した時点の本家ドキュメントにも、スキルから別スキルを呼んでも確実にロードされない旨の記載があった。その後の状況は未確認）。<br>**却下:** 依存はロード失敗の穴を塞げず「クローンすれば動く」が崩れる。ハイブリッドは存在検知ができず不具合の切り分けが難しい。<br>**条件:** design tree / frontier / ラウンド / 事実と決定の分離は grilling 由来と明記する。権利面は §5 で確認済み。 |
| D-3<br>スキルの配布形態 | プラグイン形式<br>（skills-dir） | **ラウンド 1 の決定を取り消して再検討した。** 当初「サブディレクトリ + シンボリックリンク」を選んだ根拠は「プラグイン化は導入の敷居が上がる」だったが、§5 の実験でこれが誤りと判明した。スキルディレクトリ配下に `.claude-plugin/plugin.json` があるフォルダは `<name>@skills-dir` として読み込まれ、**導入コマンドは 1 文字も変わらない**。`${CLAUDE_PLUGIN_ROOT}` で `cli.py` を共有でき、シンボリックリンクも絶対パスも不要。<br>**却下:** シンボリックリンクは全ユーザーに永続的に 1 手順を課したうえ、`${CLAUDE_SKILL_DIR}` のリンク解決という未検証の挙動に依存する。<br>**補足:** ルートの `SKILL.md` を `skills/<name>/SKILL.md` へ移し、README にマルチエージェント対応プラグインとしての導入手順を明記する。 |
| D-4<br>合意ゲートの判定 | 両方<br>（残件を機械が提示<br>→ 人間が明示合意） | 塞ぐべき失敗モードが 2 つあり、別の手段でしか塞げない。(1) 質問に答えきると AI が勝手に実装へ走り出す → 人間の明示確認でしか塞げない。(2) 未解決のまま finalize → 機械判定でしか塞げない。<br>**却下:** 機械判定のみは「全部答えたが腹落ちしていない」を拾えない。人間の確認のみは残件を人間が数えることになる。<br>**波及:** ゲートの判定条件がドリフト判定の裏返し → D-8。提示方法 → D-15。 |
| D-5<br>実装スコープ | ビルダーを作る<br>（状態管理は入れない） | ラウンド 1〜2 の実測で、design tree の SVG 手書きが最大のコストだった（約 150 行、ラウンドごとに色・ラベル・ノード・辺・レイアウトを全面的に組み直し）。加えてビルダーがないと D-1 で選んだ「ALIGNMENT.md が SSOT」がルール 1 の意味で成立しない。<br>**却下:** 状態管理は状態が四重になり、samepage の「状態は HTML と JSON にしかない」を崩す。残件は export JSON の `answers` と `comments[].status` からその場で算出する。<br>**波及:** 記法と依存の扱いが必要 → D-10、D-12。 |
| D-6<br>セッション横断の一貫性 | docs/alignment/<br>INDEX.md を置く | D-1 で A を選んだ時点で PJ の SSOT は文書の集合になり、集合に目次がないと SSOT として参照できない。索引は決定 ID・タイトル・状態と横断用語集だけを持ち、本文を持たないので二重管理にならない。<br>**却下:** 用語集だけ CONTEXT.md は書き込み先が 2 箇所になる。全部読むはセッション数に対して線形に増える。何もしないは当初の狙いを達成しない。<br>**波及:** 手で書けば必ず腐る → D-11。 |
| D-7<br>質問の提示チャネル | 材料は本文<br>問いはピン | ラウンド 1〜2 の実測で機能した。本文に材料が残るので合意後も「なぜそう決めたか」が SSOT に載り、ピンが短く保たれてパネルの一覧性が高い。<br>**却下:** ピンに全部載せると表が入らず、合意後に材料が残らない。本文に質問節を足すと二重管理になる。ピンをやめると残件を機械が数えられず D-4 が成立しない。<br>**条件:** ピンの飛び先は design tree ではなく、判断材料のある節にする。design tree のノードは該当節へのアンカーリンクにする。 |
| D-8<br>ドリフト検知のトリガー | その場 + 節目<br>（両方） | 「気づいたズレ」と「気づかなかったズレ」は別の失敗モードで、それぞれ別の手段でしか塞げない。D-4 と同じ構造の判断。<br>**却下:** 人間が言ったときだけでは、AI が気づいていても黙って進むことになる。<br>**保留:** 「何をズレとみなすか」の基準は実装を回さないと書けないので、初版は緩め（決定を明示的に破るときだけ止まる）にして運用で締める。 |
| D-9<br>スキルの名前 | grill-on-samepage | 英語の慣用句が "be *on* the same page" で、samepage 自身のタグライン "Get on the same page with your AI" も on。`grill-with-docs` の with は「成果物も作る」の意味だが、本機能の samepage は成果物ではなく面接が行われる場なので on が実態に合う。§5 で挙げた「本家の派生物と誤解される」懸念も消える。 |
| D-10<br>design tree の記法 | 入れ子の箇条書き<br>+ 規約 | Markdown ネイティブなので GitHub でそのまま木として読め、ビルダーが無くても人間が読める。状態と決定内容を行内の規約で持て、標準ライブラリだけでパースできる。<br>**却下:** mermaid は `build_readme_html.py` に前例があるように見えるが、**あれは自動生成ではなく SVG の座標もラベルも Python 側に手書き**で、mermaid ソースとは二重管理。YAML は堅いが GitHub 上の可読性を失い、標準ライブラリにパーサがない。<br>**波及:** 規約の具体 → D-13。 |
| D-11<br>INDEX.md の生成 | ビルダーが生成 | D-6 で INDEX.md を選んだ条件が「腐らないこと」だったので、ほぼ一択。`docs/alignment/*.md` を走査するだけで、D-10 の記法が決まれば実装は小さい。索引の更新忘れという失敗モードが構造的に消える。<br>**却下:** AI が合意のたびに更新する案は「手で書けば必ず腐る」がそのまま当てはまる。<br>**条件:** 人間の注記は各 ALIGNMENT 文書側に書く（INDEX.md は生成物）。 |
| D-12<br>markdown 依存の扱い | 未宣言のまま<br>+ CI で検証 | 依存宣言を増やさないので README の「サードパーティ不要」を守れ、既存の `docs/` スクリプトと一貫する。CI に `markdown` を入れるジョブを 1 つ足せば、ビルダーが無検証になる問題も同時に解ける。<br>**却下:** CI も回さない案は、SSOT を生成する経路が無検証のままになり D-1 と釣り合わない。optional extra はこのプロジェクト初の非空の依存宣言になり、`playwright` / `Pillow` の扱いとの一貫性問題を生む。自前変換は割に合わない。 |
| D-13<br>記法の具体 | 規約 5 つを採用 | インデント 2 スペースで親子。`[ID]` は文書内で一意、登場順に採番し**取り消した ID は再利用しない**。フィールド区切りは `::` でタイトル / 状態 / 決定内容。状態は `確定` / `frontier` / `再検討` / `保留` の 4 語のみで、`確定` の行だけが 3 つ目のフィールドを持つ。複数の親を持つノードは主たる親の下に置き、子として `(依存) [ID]` を足す。<br>**却下:** 絵文字案は対応表が必要になるだけで覚えることが減らず、検索しにくい。見出し案は木のインデントが使えず D-10 の理由が消える。<br>**注意:** ビルダーのパーサ契約なので、後から変えると既存の ALIGNMENT 文書を全部書き直すことになる。 |
| D-14<br>スクロール挙動の適用範囲 | 全部中央揃え | ラウンド 3 のコメントを受けて質問ジャンプを上揃えに変更したが、D-14 で取り消しの判断となった。`samepage.js` は元の `block:'center'` のまま。<br>**経緯:** 回答が以前のコメントと食い違ったため、D-8 の「AI がズレに気づいたらその場で止まる」に従って確認を挟み、「中央揃えでよい（以前の要望は撤回）」との回答を得て確定。**これが D-8 の最初の実行例。** |
| D-15<br>合意ゲートの提示方法 | 文書冒頭に<br>「残件」節を<br>ビルダーが生成 | D-1 で「合意が文書として残る」を選んだ以上、合意の可否を決める材料も文書側にあるべき。ラウンドごとに再注入するので常に最新が載り、合意時点の残件ゼロが記録として残る。<br>**却下:** ターミナルのみは会話を閉じると消え、D-1 で避けた「会話の中だけ」に戻る。「両方」は同じ情報が 2 箇所に出る。パネル案は「残件」という grill 固有の概念を samepage 本体に持ち込むので §7 の非目標の精神に反する。<br>**実装:** export JSON から算出し、`data-sp-discussion` を付けて finalize で落とす。 |

## 5. 事実確認

### 権利関係

「独立実装が権利的に問題ないか」を確認した。**問題なし。**

| 確認項目 | 結果 |
|---|---|
| mattpocock/skills | **2026-08-30 に確認した時点の表記:** MIT（Copyright (c) 2026 Matt Pocock）。`package.json` の `"license": "MIT"` とも一致していた。ここに写した年・表記が原文と一致するかは、転載や取り込みを行う前に原文で再確認する |
| samepage | MIT（Copyright (c) 2026 monasu0v0）。同一ライセンスなので取り込む場合も互換性の問題はない |
| アイデアの借用 | 著作権法の一般的な理解では、アイデアや手法そのものは著作権の保護対象ではないと考えている（法的助言ではない）。この理解のもとで、design tree / frontier / ラウンド / 事実と決定の分離は自分の言葉で書き直して使う。出典明記は義務ではなく礼儀として行う |
| 文章の転載 | 本家の文面を実質的な分量で写す場合は MIT の条件どおり著作権表示と許諾文の同梱が必要。D-2 で独立を採ったのでこの義務は発生させない |
| 名称「grill」 | 一般語であり登録商標は確認できなかった。ただし `grill-with-docs` に酷似した名前は派生物と誤解されうる → D-9 で `grill-on-samepage` に改名して解消 |

### 配布形態（D-3 の前提を崩した実験）

使い捨てのプラグインを作り、マニフェスト（Antigravity 用 `plugin.json` / Claude Code 用 `.claude-plugin/plugin.json`）と 2 つのスキルを置いてプラグイン認識を確認した。

```
sp-probe/
  plugin.json
  .claude-plugin/plugin.json
  skills/probe-one/SKILL.md
  skills/probe-two/SKILL.md
```

| 確認項目 | 結果 |
|---|---|
| 1 クローン 2 スキル | **成立する（実測）。** marketplace も install ステップも不要。README の導入コマンドは 1 クローンで完結する |
| 共有スクリプト | `SKILL.md` の 2 階層上（`../../samepage/cli.py`）または `${CLAUDE_PLUGIN_ROOT}` でプラグイン内のスキル間で共有するリソースを参照できる |
| ルート SKILL.md | **無視される（実測）。** マニフェストがある状態でルートに SKILL.md を足しても `Skills (2)` のままで、`skills/` を外すと `Skills (0)` になった。両立しない |
| 移行コスト | 説明文（`description`）による自動起動はそのまま機能し、Antigravity でも Claude Code でも他のエージェントでも同一の `skills/<name>/SKILL.md` 構造で動作する |

### リポジトリの統合面

| 確認項目 | 結果 |
|---|---|
| 再利用できるもの | `docs/build_readme_html.py` の SVG プリミティブは汎用で、`data-sp-node` と透明ヒットパスを既に出力する。ページシェル（`PAGE_CSS` / `build_page`）も再利用可能 |
| 既存の非目標と衝突 | `docs/design.md` の Non-goals に「No Markdown → HTML conversion」。**ビルダーを入れるならこの記述の書き換えが必要**（samepage CLI は変換しない / `docs/` のビルダーは別、と切り分ける） |
| 依存の現状 | `pyproject.toml` は `dependencies = []`。`markdown` は未宣言で、`build_readme_html.py` が `try/except ImportError` で案内して終了する運用 |
| CI | CI は `markdown` を入れず、ビルダーを一切実行せず、`README.html` の鮮度も検査しない → D-12 で解消 |
| SVG マーカー ID | `sp-arrow` 等が `id=` スコープなので、1 ページに 2 枚の図を置くと衝突する。ビルダーは図ごとに ID を一意化する必要がある |

## 6. 実装計画

| 順 | 作業 | 根拠 |
|---|---|---|
| 1 | プラグイン化。`plugin.json` / `.claude-plugin/plugin.json` を追加し、`SKILL.md` を `skills/samepage/` へ移動 | D-3 |
| 2 | ビルダー `docs/build_alignment_html.py`。記法のパース → design tree の SVG 生成、残件節の生成、`INDEX.md` の生成 | D-5 / D-10 / D-11 / D-13 / D-15 |
| 3 | `skills/grill-on-samepage/SKILL.md`。ラウンドの回し方、質問ピンの配置規約、確定した決定を取り消す導線、ドリフト検知、合意ゲートの手順 | D-2 / D-4 / D-7 / D-8 |
| 4 | CI ジョブ。`markdown` を入れてビルダーを実行し、生成 HTML の鮮度を検査 | D-12 |
| 5 | この文書を `.md` へ移し、ビルダーで再生成 | D-1 のルール 1 |
| 6 | ドキュメント同期。README 2 本（マルチエージェントプラグイン導入手順の記載を含む） + 生成 HTML 2 本 + `docs/design.md` + 既存 `SKILL.md` | D-3 / D-5 / D-9 |

2（ビルダー）を 5（この文書の移行）より先に置いているのは、移行先の形式がビルダーの実装で決まるため。1（プラグイン化）を最初に置いているのは、以降の `${CLAUDE_PLUGIN_ROOT}` を使ったパス記述がその構成を前提にするため。6 を最後にまとめているのは、途中で README を直すと 2 度手間になるため。

## 7. 非目標

- samepage 本体の JSON 契約（`targets[].kind`、`action`、`answers` 等）を変更しない。本機能は既存契約の上に乗る。
- Markdown → HTML 変換の**汎用**機能を samepage CLI に入れない。ビルダーは `docs/` 側のスクリプトとして、ALIGNMENT 文書という特定用途に限る。
- サーバーを立てない。`file://` で完結する。
- 実装の自動化（合意した内容からコードを生成する）は範囲外。合意までが本機能。
